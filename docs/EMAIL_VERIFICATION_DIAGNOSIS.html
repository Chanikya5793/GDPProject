Repairs included

  • Preserve send failures in recipient-scoped auth state, including a tab reload on the web. Distinguish network, rate-limit, quota, and expired-session failures without exposing raw provider details.
  • Use “verification email requested” only after Firebase acceptance. When delivery status is unknown, offer Resend and explain Inbox, Junk, and university quarantine checks without claiming delivery.
  • Coalesce concurrent requests by account and email address. Start cooldown after acceptance; do not retry sends automatically.
  • Prevent another account from inheriting a send timestamp or error. Discard late send and refresh results after an account switch.
  • Refresh verified users’ ID tokens even when the session already has emailVerified=true.
  • Add scripts/diagnose-email-verification.py, a read-only operator check that prints only public configuration and aggregate counts.

Remaining delivery proof

  1. Use an explicitly authorized address controlled by the requester, preferably @nwmissouri.edu, to request one verification message and record the request time.
  2. Inspect Inbox and Junk. If absent, obtain a university message trace/quarantine result for sender noreply@planner.chanakyachowdary.in, recipient, and timestamp. If received, inspect authentication headers and then open the verification link.
  3. If link scanning is confirmed, ask Firebase support to resolve EMAIL_TEMPLATE_UPDATE_NOT_ALLOWED so the existing confirmation handler can be activated. Do not confuse a continue URL with a handler replacement.
  4. If delivery itself is rejected, use the trace’s exact rejection to choose a correction. A custom SMTP provider is a possible later change, requiring provider access and approval for any paid service. Do not disable ownership verification to mask a delivery failure.
